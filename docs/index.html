Status and safety

Unaudited alpha; do not use with real funds. The code and storage model may change. The contract has no dispute-resolution mechanism, and an administrator may set the platform fee as high as 100%.

This repository is a small Soroban contract prototype. It implements direct token payments, an admin-managed merchant registry, platform-fee transfers, and buyer-funded escrow. It does not currently implement subscriptions, merchant update/deactivation endpoints, dispute resolution, or an on-chain refund-request process.

Only tokens exposed through a compatible Soroban token contract are supported. This is not a general-purpose bridge for arbitrary Stellar assets. Tests run in Soroban’s local test environment; this guide does not claim that a deployed contract exists.

How it works

AdminInitializes the contract, registers merchants, and updates the platform fee.
Payer / buyerAuthorizes a payment or funds a new escrow from their token balance.
Merchant / sellerReceives completed payment proceeds or released escrow funds.

Payment processing transfers the merchant’s share and fee directly from the payer. Escrow creation transfers funds into contract custody; a later release transfers them to the seller, while a seller-authorized refund returns them to the buyer.

Development setup

Prerequisites

  • Rust stable and Cargo.
  • The wasm32-unknown-unknown target for a Wasm build.
git clone https://github.com/NexaStellar/soroban-payment-gateway.git
cd soroban-payment-gateway
rustup target add wasm32-unknown-unknown
make check
make build

make check runs formatting validation, Clippy with warnings denied, and workspace tests. make build compiles a release Wasm artifact at target/wasm32-unknown-unknown/release/payment_gateway.wasm.

To see test output, run make test-verbose. No funded account or network access is needed for the contract tests.

Contract interface

MethodPurposeAuthorization
initialize(admin, platform_fee)Set the admin and initial fee once; fee is basis points (10,000 = 100%).Admin address
register_merchant(merchant_id, merchant_address, merchant_name)Add a unique merchant ID with an active status and zeroed statistics.Current admin
process_payment(payer, merchant_id, token, amount, order_id)Transfer token amounts, record the payment, update merchant volume/count, emit an event; returns a payment ID.Payer
create_escrow(buyer, seller, token, amount, order_id, release_time)Move tokens into contract custody and create an active escrow; returns an escrow ID.Buyer
release_escrow(escrow_id)Release active escrow funds to the seller.Buyer before deadline; permissionless at/after deadline
refund_escrow(escrow_id)Return active escrow funds to the buyer.Seller
get_payment(id), get_escrow(id), get_merchant(id)Read stored records as optional values.None
update_platform_fee(new_fee), get_platform_fee()Update (maximum 10,000) or read the current fee in basis points.Admin for update; none for read

Amounts use the token contract’s smallest unit and are represented as signed 128-bit integers. Payment and escrow methods reject non-positive amounts. Escrow also requires a release timestamp later than the current ledger timestamp.

Payment and escrow flows

Direct payment

  1. Initialize the contract; the admin authorizes the operation.
  2. Register the merchant using an unused ID.
  3. Call process_payment with the payer, merchant ID, token contract address, positive amount, and order ID.
  4. The payer authorizes token transfers. The contract pays the merchant amount and, when nonzero, the fee to the admin, then stores a completed payment record.

Escrow

  1. The buyer calls create_escrow, authorizing a positive token transfer to the contract and choosing a future release time.
  2. Before that time, the buyer can authorize release_escrow; the seller can instead authorize refund_escrow.
  3. At or after the release time, any caller can trigger release to the seller.
  4. Released or refunded escrows are no longer active; repeated terminal actions fail.
There is no neutral arbitrator, dispute state transition, or buyer-initiated refund operation in the current public interface. Do not treat escrow as protected against disputes.

Authorization and fee behavior

  • Initialization can only happen once. The supplied admin must authorize it.
  • Merchant registration and fee updates require the stored admin.
  • Payments require payer authorization; escrow creation requires buyer authorization.
  • Early escrow release requires buyer authorization; timed release is permissionless. Refund requires seller authorization.
  • Fee basis points are capped at 10,000. For a payment amount A, the fee is integer-rounded down from A × fee_bps / 10,000; the merchant receives A - fee.

The admin is the fee recipient. Review the current fee and contract code before interacting. This is a prototype, not a vetted payment processor.

Storage and events

The contract stores the admin, current platform fee, sequential payment and escrow IDs, merchant records, payment records, and escrow records. Merchant statistics track total volume and transaction count for successful payment calls.

Lifecycle events currently include initialized, merchant_registered, payment_processed, escrow_created, escrow_released, escrow_refunded, and fee_updated. Inspect emitted event values and the record getters for the authoritative data model.

Source layout

  • contracts/payment_gateway/src/lib.rs — contract methods and fee calculation.
  • payment.rs, escrow.rs, merchant.rs — persisted record types and statuses.
  • storage.rs — typed storage keys and accessors.
  • test.rs — local contract behavior tests.

Testing and quality checks

make test       # workspace tests
make test-verbose
make fmt-check  # formatting without modifying files
make lint       # Clippy; warnings are errors
make check      # fmt-check + lint + test

When changing contract behavior, add or update tests for authorization, rejected inputs, record status, transfers, and emitted events where relevant. Tests use Soroban’s in-process environment and a test token contract.

Contributing

Read the repository’s contribution guide, open an issue for significant changes, and include focused tests. Run make check before submitting a pull request. Never include secret keys or funded account credentials in source, logs, or issues.
